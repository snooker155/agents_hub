# Установка и запуск сервиса

Запустить сервис можно четырьмя способами. Первый подходит одному человеку,
которому сервис нужен через минуту и у которого есть только Docker. Последние
два нужны для работы с кодом. Все способы дают один и тот же сервис, и
остальная часть страницы (конфигурация, где хранится состояние, обновление,
что проверить, если сервис не запускается) относится к каждому из них.

| Способ | Что нужно | Что получится |
| --- | --- | --- |
| [A. Docker из опубликованных образов](#способ-a-docker-из-опубликованных-образов) | Docker | Дашборд на `:8080`, состояние на томе, агенты как подпроцессы. Ничего не нужно клонировать и собирать. |
| [B. Docker Compose из клона репозитория](#способ-b-docker-compose-из-клона-репозитория) | Docker, git | То же самое, но собранное из исходников, плюс отдельные контейнеры для агентов, сервис браузера, профили `postgres`, `scale` и `ha` |
| [C. Установщик](#способ-c-установщик) | Python 3.11+, Node 22+ | Виртуальное окружение, команда `ah` в PATH, дашборд с горячей перезагрузкой |
| [D. Вручную](#способ-d-вручную) | Python 3.11+, Node 22+ | Способ C, разобранный на шаги, чтобы собрать что-то своё |

Несколько бэкендов или бэкенды и воркеры на разных хостах уже не установка, а
развёртывание: варианты описаны в [deployment](deployment.md).

Любой из способов A, B и C можно настроить и ответами на вопросы: см.
[пошаговую настройку](#пошаговая-настройка-ah-setup) ниже.

## Требования

| Инструмент | Версия | Для чего нужен |
| --- | --- | --- |
| Docker + Compose | любая свежая | Способы A и B, а также запуск агентов в Docker на способах C и D |
| Python | 3.11+ | Способы C и D: бэкенд, CLI, запуск агентов |
| Node.js + npm | 22+ | Способы C и D: дашборд |
| Ключ провайдера | | OpenAI, Anthropic, Google или локальный Ollama / LM Studio. Можно добавить в Настройках после запуска |

## Способ A: Docker из опубликованных образов

Каждый релиз публикует бэкенд и дашборд как образы в GHCR
(`ghcr.io/snooker155/agents-hub-backend`, `ghcr.io/snooker155/agents-hub-frontend`),
а в репозитории в `deploy/quickstart/` лежит compose-файл, который запускает
оба для одного человека. Ничего не нужно клонировать и собирать:

```bash
mkdir agents-hub && cd agents-hub
curl -fsSLO https://raw.githubusercontent.com/snooker155/agents_hub/main/deploy/quickstart/docker-compose.yml
curl -fsSL  https://raw.githubusercontent.com/snooker155/agents_hub/main/deploy/quickstart/env.example -o .env
docker compose up -d
```

Откройте `http://localhost:8080`, введите ключ провайдера в Настройках (или
раскомментируйте его в `.env` до запуска), выберите агента в Чате и отправьте
сообщение.

Что работает: бэкенд, в котором каждый агент запускается как его подпроцесс
(`AGENT_EXECUTION_MODE=local`), и дашборд за nginx, который также проксирует
`/api`. Состояние хранится в именованном томе `agents_hub_data`, поэтому
`docker compose down` его сохраняет, а `docker compose down -v` удаляет.
`.env` смонтирован в бэкенд как тот файл, в который пишут Настройки, так что
ключи, введённые на этой странице, переживают контейнер. `WEB_PORT` в `.env`
меняет порт дашборда, `AGENTS_HUB_TAG` закрепляет релиз вместо `latest`
(`0.8` для последнего патча этой минорной версии, `0.8.0` ровно для этой
версии, `0.8.0-rag` для варианта со стеком RAG, см.
[deployment](deployment.md), раздел "Releases"), а `DEMO_WORKSPACE=1` при
первом запуске создаёт [демо-пространство](demo.md).

```bash
docker compose pull && docker compose up -d                     # upgrade
docker compose exec backend python -m cli db backup --to /data/backups
docker compose logs -f backend
```

Терминальный клиент работает с этой установкой по REST: в клоне репозитория
`pip install -e .` ставит `ah` всего с тремя зависимостями, затем выполните
`export AGENTS_HUB_URL=http://localhost:8080` ([cli](cli.md), раздел "Two ways
it reaches the service"). Или обращайтесь к API через `docker compose exec
backend python -m cli ...` внутри контейнера.

Чего в этом варианте нет: сокет Docker не смонтирован, поэтому агенты не
могут получить собственные контейнеры ([containers](containers.md));
провайдеру песочницы `docker` и сервису браузера нужен способ B; в образе без
суффикса `-rag` нет стека эмбеддингов, поэтому `RAG_VECTOR_DB` остаётся
`none`, пока вы не закрепите тег `-rag`.

## Способ B: Docker Compose из клона репозитория

```bash
git clone https://github.com/snooker155/agents_hub.git
cd agents_hub
docker compose up --build              # backend :8000, dashboard :8080
```

`.env` здесь не обязателен: стек поднимается без ключей провайдеров, а ключи
вы добавляете в Настройках. `BACKEND_PORT` и `WEB_PORT` меняют опубликованные
порты, и дашборд подстраивается сам, потому что обращается к своему же
источнику. Клон смонтирован в бэкенд, поэтому состояние попадает в
`.agents_hub/` внутри него, как при локальной установке, а обновление сводится
к `git pull` и `docker compose up -d --build`. Сокет Docker смонтирован,
поэтому агенты могут работать в собственных контейнерах
(`AGENT_EXECUTION_MODE=docker`, [containers](containers.md)). `WITH_RAG=true`
в `.env` собирает образ со стеком RAG.

Дашборд здесь собранный бандл за nginx, который также проксирует `/api` и
распределяет запросы между бэкендами за ним. Поэтому добавить бэкенды можно
одним флагом:

```bash
docker compose --profile scale up --build --scale backend=3
```

В том же файле необязательные сервисы описаны как профили: `postgres`
(база данных вместо SQLite, [scaling](scaling.md)), `scale` (Redis, чтобы
реплик бэкенда было больше одной), `browser` (headless Chromium для
инструментов браузера) и `ha` (Postgres, Redis, MinIO, реплики `api` и
`worker`: вариант высокой доступности из [deployment](deployment.md)).

Сервиса Vite в Compose нет. Чтобы при правке фронтенда работал HMR, запустите
`npm run dev` на хосте, как в способе C, а когда изменение должно попасть в
контейнер, пересоберите образ (`docker compose up --build frontend`).

## Способ C: установщик

```bash
git clone https://github.com/snooker155/agents_hub.git
cd agents_hub
./install.sh
```

Установщик создаёт `.venv`, ставит сервис и команду `ah` в редактируемом
режиме, копирует `.env.example` в `.env`, если `.env` ещё нет, ставит
npm-пакеты дашборда и записывает интеграцию с оболочкой в её стартовый файл.
Его можно запускать повторно: существующий `.env` никогда не перезаписывается,
а блок оболочки обновляется на месте, а не дописывается ещё раз.

Флаги: `--no-frontend` (сервис без npm-пакетов дашборда), `--cli-only`
(только клиент для работы с `AGENTS_HUB_URL`, тоже без дашборда),
`--with-rag` (добавляет зависимости RAG, они тянут за собой torch),
`--with-demo` (включает `DEMO_WORKSPACE` в `.env`, и при первом запуске
сервиса создаётся демо-пространство, см. [demo](demo.md)),
`--setup` / `--no-setup` ([пошаговая настройка](#пошаговая-настройка-ah-setup):
без флага она запускается при первой установке из терминала и сама
записывает `.env`),
`--no-venv`, `--no-shell`, `--venv PATH`, `--python PATH`.

Затем в новом терминале:

```bash
ah up                       # API on :8000, dashboard on :5173
```

## Способ D: вручную

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e ".[backend,agents]"     # service + the ah command
cp .env.example .env
cd dashboard/frontend && npm install && cd ../..
```

Один `pip install -e .` ставит только терминальный клиент и три его
зависимости. Наборы дополнительных зависимостей читаются из файлов
requirements в репозитории, поэтому `[backend]`, `[agents]` и `[rag]` всегда
совпадают с ними.

`[connectors]` добавляет драйверы, нужные коннекторам (MySQL, ClickHouse,
msal, google-auth; `requirements-connectors.txt`).

`requirements.lock` фиксирует точное разрешение этих файлов requirements (без
`rag`, `postgres` и `connectors`) для Python 3.11 и 3.12. Из него ставятся
Docker-образ бэкенда и CI, а `pip install -r requirements.lock` вручную
воспроизводит то же окружение.

Редактируемый режим выбран намеренно: команда следует за клоном, в том числе
после `git pull`, а не замораживает копию. В site-packages попадает один
пакет, `agents_hub`. Его единственная задача: добавить клон в `sys.path` и
передать управление пакету `cli`.

Вообще без установки `python -m cli` в клоне работает как та же программа, а
два сервера запускаются напрямую:

```bash
python -m uvicorn dashboard.backend.main:app --host 0.0.0.0 --port 8000
cd dashboard/frontend && npm run dev -- --host 0.0.0.0 --port 5173
```

## Пошаговая настройка (`ah setup`)

`ah setup` проводит через всю установку вопросами, как первый запуск
OpenClaw, и ничего не записывает, пока вы не подтвердите сводку всех значений:

1. **Установка**: этот клон (способ C), Docker из опубликованных образов
   (способ A, в выбранную вами папку), Compose из этого клона (способ B)
   или хаб, который уже работает в другом месте. Затем QuickStart (только то,
   что нельзя угадать: остальное ассистент настроит вместе с вами, см.
   [после установки](#после-установки-дальше-ведёт-ассистент)) или Advanced.
2. **База данных**: SQLite; Postgres в Docker-контейнере, который настройка
   запустит сама (на этой машине) или в том же стеке (способы с Docker,
   профиль `postgres`); или уже существующий Postgres, который проверяется,
   прежде чем будет принят. Существующее состояние SQLite можно перенести
   (`ah db migrate`).
3. **Доступ**: без входа, один общий токен (генерируется) или учётные записи:
   первый администратор и другие люди, а в Advanced ещё и единый вход.
   `AGENTS_HUB_SECRET_KEY` генерируется один раз, и повторный запуск его не
   меняет.
4. **Провайдеры и модели**: OpenAI, Anthropic, Google, Ollama, LM Studio.
   Каждый ключ или адрес проверяется запросом списка моделей у провайдера.
   Модель по умолчанию выбирается из пресетов, сверенных с этим списком
   (сбалансированная, самая сильная, самая быстрая), из всего списка или
   вводится вручную. На этой машине пресеты также включаются в каталоге
   [Модели](models.md), а модель по умолчанию отмечается звёздочкой.
5. **Голос ассистента**: чем [ассистент](assistant.md#voice) вас слышит и чем
   читает свои ответы вслух. Выбор сохраняется как модели распознавания и
   синтеза речи пространства `default` (все личные пространства берут их,
   если своих нет). Варианты: облачный провайдер, выбранный на шаге 4
   (OpenAI: `gpt-4o-mini-tts` и `gpt-4o-mini-transcribe` с их ценами; Google:
   Gemini TTS и Gemini Flash) с одним из его голосов; собственная среда
   моделей хаба (для распознавания Whisper small или large-v3 turbo, для речи
   Piper на русском, английском или немецком, Kokoro, Supertonic на 31 языке
   или Kitten на английском; бесплатно, скачать нужно от 0,5 до 2 ГБ); только
   браузер (его собственное распознавание и голос, на сервере ничего); или
   «не сейчас». В QuickStart этот шаг остаётся ассистенту.
6. **Возможности**: в Advanced демо-пространство, порт дашборда, где
   запускаются агенты, веб-поиск, RAG, а для Compose ещё браузер и Redis.
   В QuickStart демо и веб-поиск остаются ассистенту.
7. **Сводка** всех настроек, которые будут записаны (секреты скрыты), и всех
   действий, которые будут выполнены.
8. **Применение**: ставит недостающие зависимости Python, запускает Postgres,
   записывает `.env` (прежний сохраняется как `.env.bak-<time>`), создаёт
   учётные записи, заполняет каталог, задаёт голос ассистента и предлагает
   запустить хаб (`ah up` или `docker compose up -d`, после чего учётные
   записи создаются и голос задаётся через API). Для голоса на среде моделей
   хаба настройка запускает среду, ставит недостающие движки и скачивает
   недостающие модели, дожидаясь конца каждой задачи. В Docker для этого
   нужен работающий стек, поэтому, если его не запускать, голос остаётся на
   следующий запуск настройки или на страницу Модели. После настройки Docker
   можно направить `ah` на стек с личным API-ключом нового администратора.

Если в файле ответов указаны `voice.mode` или `demo`, они применяются и в
QuickStart.

### Первый запуск в браузере

С одним оператором (`AUTH_MODE=single` или `token`) новая установка
открывается на отдельном экране настройки вместо приложения: без боковой
панели и шапки, одно решение на экран, как при первом включении телефона.
По порядку: приветствие, язык, светлое или тёмное оформление, модель,
модель по умолчанию, голос ассистента, поиск в интернете, личная память и
демо-пространство, затем сводка и вход (**Начать работу**, **Продолжить с
ассистентом** или **Пройти обзор**).

На экране голоса вы знакомитесь с ассистентом: он здоровается вслух, каждым
языком своим голосом ([голос для каждого языка](assistant.md)), вы отвечаете,
слышно ли его, говорите что-нибудь голосом и слышите ответ; так одним разом
проверяются модель, синтез и распознавание речи. Дальше на каждом экране внизу
есть ассистент, его можно спросить об этом экране голосом или текстом, а
последний экран передаёт работу ему, голосом, если его было слышно.

Обязательна только модель: ключ OpenAI, Anthropic или Google (проверяется у
провайдера до сохранения), сервер моделей, уже запущенный на этом
компьютере (Ollama, LM Studio; его модели показываются списком), или, если
у хаба своя среда для моделей, готовый локальный набор, который скачивается
в фоне. На каждом следующем экране есть **Не сейчас**, а экран, ответ на
который уже есть (ключ из `ah setup`, поиск через ключ модели), просто
сообщает об этом. Пропустить настройку целиком нельзя.

Шаг сохраняется в хабе, поэтому после перезагрузки или в другом браузере
настройка продолжается с того же места; выбранные язык и оформление
получает и новый браузер. Пройденная настройка больше не появляется;
**Настройки, Первая настройка** запускает её снова. Установку, которой уже
пользовались до обновления (есть чат или начатая настройка с ассистентом),
она не останавливает. В режиме `multi` первый администратор создаётся на
экране входа, а каждый человек видит окно приветствия, описанное ниже.

### После установки: дальше ведёт ассистент

Консоль (или браузер) делает только то, чего ассистент не может сделать сам:
создаёт учётную запись и подключает одну модель, которой он будет думать.
С одним оператором это делает первый запуск выше, а его кнопка **Продолжить
с ассистентом** ведёт сюда. В режиме `multi`, когда человек впервые
открывает дашборд, окно приветствия либо просит эту модель
(ключ OpenAI, Anthropic или Google или сервер моделей, уже работающий на этой
машине; перед сохранением он проверяется у провайдера), либо, если модель уже
есть, предлагает **Говорить с ассистентом** или **Печатать ассистенту**.
Дальше [ассистент](assistant.md#guided-setup) ведёт остальную настройку по
одному шагу, голосом или текстом: модель по умолчанию, его собственный голос,
веб-поиск, демо-пространство, команда, состояние хаба, затем первый чат,
канал, учётные записи, ваш собственный агент, задача и то, что работает само.
Каждое изменение он делает после вашего «да» в карточке. Ключи вводятся в
карточку, их никогда не произносят и не пишут в разговоре. Страница каждого
шага открывается рядом с разговором. Плашка **Настройка** в шапке показывает,
сколько уже сделано, и возвращает к настройке.

`./install.sh` сам запускает её при первой установке из терминала
(`--no-setup` пропускает, `--setup` запускает при повторной установке).
Запускайте её снова, когда нужно поменять настройку: каждый вопрос тогда
предлагает действующее значение, а пустой ответ на вопрос о ключе оставляет
текущий ключ.

```bash
ah setup                       # ask
ah setup --shape docker --dir ~/agents-hub
ah setup --dry-run             # stop after the review
ah setup --answers setup.json  # unattended, see below
ah setup --disconnect          # forget a hub the remote shape saved
```

Для установки без участия человека у каждого вопроса есть ключ, и файл
ответов задаёт ответы по этим ключам. Всё, чего в нём нет, получает значение
по умолчанию, а отсутствие обязательного ответа останавливает настройку с
указанием его имени:

```json
{
  "shape": "docker",
  "dir": "/srv/agents-hub",
  "database": "postgres-bundled",
  "auth": "multi",
  "admin": {"username": "admin", "password": "change-me-now"},
  "users": [{"username": "dana", "role": "member"}],
  "providers": {"anthropic": {"api_key": "sk-ant-...", "model": "claude-sonnet-5"}},
  "voice": {"mode": "local", "speech": "piper-en", "transcription": "whisper-small"},
  "demo": false,
  "start": true
}
```

`voice.mode` принимает значения `cloud` (с `voice.provider`, если подходят
два, и `voice.voice`), `local` (`voice.speech`: `piper-ru`, `piper-en`,
`piper-de`, `kokoro`, `supertonic` или `kitten`; `voice.transcription`:
`whisper-small` или `whisper-turbo`), `browser` или `skip`. Неуказанные пароли
генерируются и один раз печатаются в конце. Вариант с удалённым хабом
сохраняет адрес хаба и учётные данные в собственном файле состояния CLI
(`~/.config/agents-hub/cli.json`); `AGENTS_HUB_URL` в окружении по-прежнему
важнее.

## Конфигурация

`.env` читается при запуске. Минимум: провайдер и ключ.

```env
DEFAULT_PROVIDER=openai
OPENAI_API_KEY=sk-...
OPENAI_MODEL=gpt-5
AGENT_EXECUTION_MODE=local
```

В `.env.example` перечислены все переменные со значениями по умолчанию.
Большую часть потом можно менять в дашборде, и разделение стоит запомнить
сразу: в [settings](settings.md) хранятся учётные данные, а в
[models](models.md) каталог, то есть какие модели предлагаются, сколько стоит
каждая и какая модель у каждого провайдера по умолчанию.

## Проверка, что всё работает

```bash
curl http://localhost:8000/api/health   # database, background services, state size
ah config                               # which service the CLI is talking to
ah agent list                           # the seeded system agents
```

В Docker (способы A и B) API доступен и через nginx дашборда, поэтому
`curl http://localhost:8080/api/health` отвечает так же. Откройте
`http://localhost:5173` (`http://localhost:8080` в Docker), выберите агента в
Чате и отправьте сообщение. Если пришёл ответ, значит, ключ провайдера,
каталог моделей и конвейер запусков работают. Если запуск упал,
[service-health](service-health.md) покажет, какая часть отказала.

## Где хранится состояние

Всё, что пишет сервис, попадает в `.agents_hub/` внутри клона:
`agents_hub.db` (SQLite в режиме WAL: реестр агентов, каталог моделей,
потоки, запуски, задачи, сессии, пулы памяти и все остальные записи), папки
рабочих пространств, логи запусков и созданные представления. Удаление этой
папки сбрасывает установку; эту же папку нужно бэкапить ([backup](backup.md)).
В способе A то же дерево лежит на томе `agents_hub_data`, смонтированном в
`/data` (`AGENTS_HUB_ROOT`). Если задан `AGENTS_HUB_DATABASE_URL`, база данных
хранится не в файле, а в Postgres ([scaling](scaling.md); перенести
существующую базу можно через `ah db migrate`), а остальное содержимое папки
остаётся на месте. Промпты агентов разделены так же: текст системных агентов
лежит в `agents/definitions/<id>/` в репозитории, в том виде, в каком его
отслеживает git, и хаб туда никогда не пишет. `instructions.md` (вместе с
`capabilities.md` и `usage.md`) каждого нового агента и любая правка промпта
системного агента попадают в `.agents_hub/definitions/<id>/`. Файл там
перекрывает одноимённый файл из репозитория, поэтому правка системного агента
переживает обновление. Кнопка **Вернуть исходный текст** на вкладке Config
агента (`DELETE /api/agents/<id>/definition/edits`) возвращает исходный текст,
а изменённый сохраняет во вкладке «Версии».

## Обновление

| Способ | Обновление |
| --- | --- |
| A | `docker compose pull && docker compose up -d` |
| B | `git pull && docker compose up -d --build` |
| C | `git pull && ./install.sh` (подтягивает новые зависимости; `.env` не трогается) |
| D | `git pull && pip install -e ".[backend,agents]"`, `npm install` в дашборде |

При редактируемой установке изменения кода не требуют переустановки.
Изменения схемы применяются сами: первое подключение в любом процессе
приводит схему в порядок, так что их может применить и бэкенд, и команда CLI.
База SQLite архивируется перед миграцией, и релиз с миграциями нельзя откатить
без этого архива. Поэтому сначала прочитайте **Upgrade notes** релиза в
[changelog](changelog.md), а полную процедуру смотрите в
[deployment](deployment.md) (разделы "Upgrading" и "Rolling back").

## Если сервис не запускается

- **Бэкенд сразу завершается.** Виртуальное окружение не активировано или
  дополнительные зависимости не установлены. Выполните
  `pip install -e ".[backend,agents]"` ещё раз и прочитайте вывод.
- **Дашборд не достаёт до API.** Он обращается к `http://localhost:8000/api`.
  Проверьте, что бэкенд слушает этот порт и что его не блокирует локальная
  настройка CORS.
- **Запуски падают сразу после старта.** Ключа провайдера нет или он неверный,
  модель не включена на странице [models](models.md) или задан
  `AGENT_EXECUTION_MODE=docker`, а демон Docker недоступен.
- **`ah` не найдена.** Виртуальное окружение не в PATH, и хук оболочки не
  установлен. Выполните `ah shell-init --install` из виртуального окружения
  или вызывайте скрипт по абсолютному пути. См. [cli](cli.md).
- **Способ A: `unable to open database file`.** Не отработал шаг `init`,
  который передаёт том пользователю бэкенда. Повторный `docker compose up -d`
  запустит его снова (шаг идемпотентен), а `docker compose logs init` покажет,
  почему он упал.
- **Способ A: `.env` оказался папкой.** Docker создал её, потому что при
  первом запуске стека файла не было. Выполните `docker compose down` и
  `rmdir .env`, сохраните шаблон как `.env` и запустите снова.
