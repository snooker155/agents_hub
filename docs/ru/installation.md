# Установка и запуск сервиса

Запустить сервис можно тремя способами. Первый это Docker Compose из клона
репозитория, последние два нужны для работы с кодом. Все способы дают один и тот же сервис, и
остальная часть страницы (конфигурация, где хранится состояние, обновление,
что проверить, если сервис не запускается) относится к каждому из них.

| Способ | Что нужно | Что получится |
| --- | --- | --- |
| [A. Docker Compose из клона репозитория](#способ-a-docker-compose-из-клона-репозитория) | Docker, git | Дашборд на `:8080` и API на `:8000`, собранные из исходников, плюс отдельные контейнеры для агентов |
| [B. Установщик](#способ-b-установщик) | Python 3.11+, Node 22+ | Виртуальное окружение, команда `ah` в PATH, дашборд с горячей перезагрузкой |
| [C. Вручную](#способ-c-вручную) | Python 3.11+, Node 22+ | Способ B, разобранный на шаги, чтобы собрать что-то своё |

Любой из способов A, B и C можно настроить и ответами на вопросы: см.
[пошаговую настройку](#пошаговая-настройка-ah-setup) ниже.

## Требования

| Инструмент | Версия | Для чего нужен |
| --- | --- | --- |
| Docker + Compose | любая свежая | Способ A, а также запуск агентов в Docker на способах B и C |
| Python | 3.11+ | Способы B и C: бэкенд, CLI, запуск агентов |
| Node.js + npm | 22+ | Способы B и C: дашборд |
| Ключ провайдера | | OpenAI, Anthropic, Google или локальный Ollama / LM Studio. Можно добавить в Настройках после запуска |

## Способ A: Docker Compose из клона репозитория

```bash
git clone -b lite https://github.com/snooker155/agents_hub.git
cd agents_hub
docker compose up --build              # backend :8000, dashboard :8080
```

`.env` здесь не обязателен: стек поднимается без ключей провайдеров, а ключи
вы добавляете в Настройках. `BACKEND_PORT` и `WEB_PORT` меняют опубликованные
порты, и дашборд подстраивается сам, потому что обращается к своему же
источнику. Клон смонтирован в бэкенд, поэтому состояние попадает в
`.agents_hub/` внутри него, как при локальной установке, а обновление сводится
к `git pull` и `docker compose up -d --build`. Сокет Docker смонтирован,
поэтому агенты могут работать в собственных контейнерах
(`AGENT_EXECUTION_MODE=docker`, [containers](containers.md)). `WITH_RAG=true`
в `.env` собирает образ со стеком RAG.

Compose тоже не ставит `ah` на хост: `docker compose exec backend ah ...`
запускает её в контейнере, а клиент на хосте ставится отдельно, см. [команда `ah` на каждом способе](#команда-ah-на-каждом-способе).

Дашборд здесь собранный бандл за nginx, который также проксирует `/api`.

Сервиса Vite в Compose нет. Чтобы при правке фронтенда работал HMR, запустите
`npm run dev` на хосте, как в способе B, а когда изменение должно попасть в
контейнер, пересоберите образ (`docker compose up --build frontend`).

## Способ B: установщик

```bash
git clone -b lite https://github.com/snooker155/agents_hub.git
cd agents_hub
./install.sh
```

Установщик создаёт `.venv`, ставит сервис и команду `ah` в редактируемом
режиме, копирует `.env.example` в `.env`, если `.env` ещё нет, ставит
npm-пакеты дашборда и записывает интеграцию с оболочкой в её стартовый файл.
Его можно запускать повторно: существующий `.env` никогда не перезаписывается,
а блок оболочки обновляется на месте, а не дописывается ещё раз.

Флаги: `--no-frontend` (сервис без npm-пакетов дашборда), `--cli-only`
(только клиент для работы с `AGENTS_HUB_URL`, тоже без дашборда),
`--with-rag` (добавляет зависимости RAG, они тянут за собой torch),
`--with-demo` (включает `DEMO_WORKSPACE` в `.env`, и при первом запуске
сервиса создаётся демо-пространство, см. [demo](demo.md)),
`--setup` / `--no-setup` ([пошаговая настройка](#пошаговая-настройка-ah-setup):
без флага она запускается при первой установке из терминала и сама
записывает `.env`),
`--no-venv`, `--no-shell`, `--venv PATH`, `--python PATH`.

Затем в новом терминале:

```bash
ah up                       # API on :8000, dashboard on :5173
```

## Способ C: вручную

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e ".[backend,agents]"     # service + the ah command
cp .env.example .env
cd dashboard/frontend && npm install && cd ../..
```

Один `pip install -e .` ставит только терминальный клиент и три его
зависимости. Наборы дополнительных зависимостей читаются из файлов
requirements в репозитории, поэтому `[backend]`, `[agents]` и `[rag]` всегда
совпадают с ними.

`requirements.lock` фиксирует точное разрешение этих файлов requirements (без
`rag`) для Python 3.11 и 3.12. Из него ставятся
Docker-образ бэкенда и CI, а `pip install -r requirements.lock` вручную
воспроизводит то же окружение.

Редактируемый режим выбран намеренно: команда следует за клоном, в том числе
после `git pull`, а не замораживает копию. В site-packages попадает один
пакет, `agents_hub`. Его единственная задача: добавить клон в `sys.path` и
передать управление пакету `cli`.

Вообще без установки `python -m cli` в клоне работает как та же программа, а
два сервера запускаются напрямую:

```bash
python -m uvicorn dashboard.backend.main:app --host 0.0.0.0 --port 8000
cd dashboard/frontend && npm run dev -- --host 0.0.0.0 --port 5173
```

## Команда `ah` на каждом способе

`ah` обращается к сервису одним из двух способов ([cli](cli.md), раздел
"Two ways it reaches the service"): **напрямую**, в процессе, у которого
есть клон репозитория, его Python-зависимости и каталог состояния, или
**по REST**, к работающему бэкенду, адрес которого задан в `AGENTS_HUB_URL`.
Что из этого доступно, зависит от способа установки:

| Способ | `ah` на хосте | `ah` в контейнере бэкенда |
| --- | --- | --- |
| A. Compose из клона | Не установлена. Добавьте клиент (ниже), REST на `http://localhost:8080` или `:8000` | `docker compose exec backend ah ...`, напрямую |
| B. Установщик | В PATH в новом терминале, напрямую | |
| C. Вручную | В активированном venv после `pip install -e ...`, напрямую; без установки `python -m cli` из клона | |

Прямой режим на хосте до Docker-установки не дотягивается. В способе A база в смонтированном клоне принадлежит бэкенду в контейнере:
второму процессу на хосте нужны те же зависимости и настройки, а на macOS и
Windows блокировки SQLite не работают через общий доступ к файлам Docker
Desktop. Поэтому в способе A хост работает по REST, а команды, которым нужен
прямой режим, запускаются в контейнере: `ah db ...`. `ah up` и `ah server start` запускают сервис на этой
машине и к Docker-установке не относятся.

### Как добавить `ah` к Docker-установке

**В контейнере** добавлять нечего: в образе бэкенда есть `ah` (та же программа
вызывается как `python -m cli`). Она работает напрямую, с той же базой и тем же томом, что
и бэкенд:

```bash
docker compose exec backend ah doctor
docker compose exec backend ah db status
alias ah='docker compose -f ~/agents-hub/docker-compose.yml exec backend ah'
```

С таким алиасом `ah` в любой папке хоста означает команду в контейнере;
пути, которые ей передают, тогда пути внутри контейнера.

**На хосте** клиенту по REST нужны клон репозитория (в способе A он уже
есть) и Python 3.11+, но не зависимости сервиса:

```bash
git clone -b lite https://github.com/snooker155/agents_hub.git && cd agents_hub
./install.sh --cli-only        # .venv с ah и тремя её зависимостями, хук оболочки
export AGENTS_HUB_URL=http://localhost:8080
ah config                      # показывает, с каким сервисом она работает
ah agent list
```

Новая установка учётных данных не спрашивает. Пути по REST разрешает бэкенд,
поэтому папку хоста сначала нужно смонтировать в контейнер ([cli](cli.md),
раздел "Against a containerized backend").

Если на хосте нет Python, `scripts/build_cli_binary.sh` на машине, где он
есть, собирает `ah` одним файлом, только для REST, и этот файл можно
скопировать куда угодно ([cli](cli.md), раздел "A binary, for REST mode
without a venv").

## Пошаговая настройка (`ah setup`)

`ah setup` проводит через всю установку вопросами, как первый запуск
OpenClaw, и ничего не записывает, пока вы не подтвердите сводку всех значений:

1. **Установка**: единственный вариант в этой редакции, эта машина из этого
   клона (виртуальное окружение, `ah up`). Затем QuickStart (только то, что
   нельзя угадать) или Advanced.
2. **Провайдеры и модели**: OpenAI, Anthropic, Google, Ollama, LM Studio.
   Каждый ключ или адрес проверяется запросом списка моделей у провайдера.
   Модель по умолчанию выбирается из пресетов, сверенных с этим списком
   (сбалансированная, самая сильная, самая быстрая), из всего списка или
   вводится вручную. На этой машине пресеты также включаются в каталоге
   [Модели](models.md), а модель по умолчанию отмечается звёздочкой.
3. **Возможности**: демо-пространство, а в Advanced ещё где запускаются
   агенты (локальными процессами или по контейнеру на каждого) и RAG.
4. **Сводка** всех настроек, которые будут записаны (секреты скрыты), и всех
   действий, которые будут выполнены.
5. **Применение**: ставит недостающие зависимости Python, записывает `.env`
   (прежний сохраняется как `.env.bak-<time>`), заполняет каталог и
   предлагает запустить хаб (`ah up`).

Если в файле ответов указан `demo`, он применяется и в QuickStart.

### Первый запуск в браузере

Новая установка
открывается на отдельном экране настройки вместо приложения: без боковой
панели и шапки, одно решение на экран, как при первом включении телефона.
По порядку: приветствие, язык, светлое или тёмное оформление,
ключ модели и модель по умолчанию, личная память и демо-пространство,
затем сводка и вход (**Начать работу** или **Пройти обзор**).

Обязательна только модель: ключ OpenAI, Anthropic или Google (проверяется у
провайдера до сохранения), сервер моделей, уже запущенный на этом
компьютере (Ollama, LM Studio; его модели показываются списком). На каждом
следующем экране есть **Не сейчас**, а экран, ответ на
который уже есть (ключ из `ah setup`), просто
сообщает об этом.

Шаг сохраняется в хабе, поэтому после перезагрузки или в другом браузере
настройка продолжается с того же места; выбранные язык и оформление
получает и новый браузер. Пройденная настройка больше не появляется;
**Настройки, Первая настройка** запускает её снова. Установку, которой уже
пользовались до обновления (есть чат),
она не останавливает.

`./install.sh` сам запускает её при первой установке из терминала
(`--no-setup` пропускает, `--setup` запускает при повторной установке).
Запускайте её снова, когда нужно поменять настройку: каждый вопрос тогда
предлагает действующее значение, а пустой ответ на вопрос о ключе оставляет
текущий ключ.

```bash
ah setup                       # ask
ah setup --advanced            # skip the QuickStart question
ah setup --dry-run             # stop after the review
ah setup --answers setup.json  # unattended, see below
```

Для установки без участия человека у каждого вопроса есть ключ, и файл
ответов задаёт ответы по этим ключам. Всё, чего в нём нет, получает значение
по умолчанию, а отсутствие обязательного ответа останавливает настройку с
указанием его имени:

```json
{
  "shape": "local",
  "providers": {"anthropic": {"api_key": "sk-ant-...", "model": "claude-sonnet-5"}},
  "demo": false,
  "start": true
}
```

## Конфигурация

`.env` читается при запуске. Минимум: провайдер и ключ.

```env
DEFAULT_PROVIDER=openai
OPENAI_API_KEY=sk-...
OPENAI_MODEL=gpt-5
AGENT_EXECUTION_MODE=local
```

В `.env.example` перечислены все переменные со значениями по умолчанию.
Большую часть потом можно менять в дашборде, и разделение стоит запомнить
сразу: в [settings](settings.md) хранятся учётные данные, а в
[models](models.md) каталог, то есть какие модели предлагаются, сколько стоит
каждая и какая модель у каждого провайдера по умолчанию.

## Проверка, что всё работает

```bash
curl http://localhost:8000/api/health   # database, background services, state size
ah config                               # which service the CLI is talking to
ah agent list                           # the seeded system agents
```

В Docker (способ A) API доступен и через nginx дашборда, поэтому
`curl http://localhost:8080/api/health` отвечает так же. Откройте
`http://localhost:5173` (`http://localhost:8080` в Docker), выберите агента в
Чате и отправьте сообщение. Если пришёл ответ, значит, ключ провайдера,
каталог моделей и конвейер запусков работают. Если запуск упал,
[service-health](service-health.md) покажет, какая часть отказала.

## Где хранится состояние

Всё, что пишет сервис, попадает в `.agents_hub/` внутри клона:
`agents_hub.db` (SQLite в режиме WAL: реестр агентов, каталог моделей,
потоки, запуски, задачи, сессии, пулы памяти и все остальные записи), папки
рабочих пространств, логи запусков и созданные представления. Удаление этой
папки сбрасывает установку; эту же папку нужно бэкапить ([backup](backup.md)).
Промпты агентов разделены так же: текст системных агентов
лежит в `agents/definitions/<id>/` в репозитории, в том виде, в каком его
отслеживает git, и хаб туда никогда не пишет. `instructions.md` (вместе с
`capabilities.md` и `usage.md`) каждого нового агента и любая правка промпта
системного агента попадают в `.agents_hub/definitions/<id>/`. Файл там
перекрывает одноимённый файл из репозитория, поэтому правка системного агента
переживает обновление. Кнопка **Вернуть исходный текст** на вкладке Config
агента (`DELETE /api/agents/<id>/definition/edits`) возвращает исходный текст,
а изменённый сохраняет во вкладке «Версии».

## Обновление

| Способ | Обновление |
| --- | --- |
| A | `git pull && docker compose up -d --build` |
| B | `git pull && ./install.sh` (подтягивает новые зависимости; `.env` не трогается) |
| C | `git pull && pip install -e ".[backend,agents]"`, `npm install` в дашборде |

При редактируемой установке изменения кода не требуют переустановки.
Изменения схемы применяются сами: первое подключение в любом процессе
приводит схему в порядок, так что их может применить и бэкенд, и команда CLI.
База SQLite архивируется перед миграцией, и релиз с миграциями нельзя откатить
без этого архива. Поэтому сначала прочитайте **Upgrade notes** релиза в
описании релиза, а полную процедуру смотрите в
[deployment](deployment.md) (разделы "Upgrading" и "Rolling back").

## Если сервис не запускается

- **Бэкенд сразу завершается.** Виртуальное окружение не активировано или
  дополнительные зависимости не установлены. Выполните
  `pip install -e ".[backend,agents]"` ещё раз и прочитайте вывод.
- **Дашборд не достаёт до API.** Он обращается к `http://localhost:8000/api`.
  Проверьте, что бэкенд слушает этот порт и что его не блокирует локальная
  настройка CORS.
- **Запуски падают сразу после старта.** Ключа провайдера нет или он неверный,
  модель не включена на странице [models](models.md) или задан
  `AGENT_EXECUTION_MODE=docker`, а демон Docker недоступен.
- **`ah` не найдена.** Виртуальное окружение не в PATH, и хук оболочки не
  установлен. Выполните `ah shell-init --install` из виртуального окружения
  или вызывайте скрипт по абсолютному пути. См. [cli](cli.md). В способе A
  на хосте `ah` нет, пока вы её не добавите, см.
  [команда `ah` на каждом способе](#команда-ah-на-каждом-способе).
