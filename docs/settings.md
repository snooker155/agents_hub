# Settings

Credentials and connection details. What models are offered and which is default
lives on the [models](models.md) page, not here.

## What is here

- **API keys** per provider, and the base URL when it is not the default.
- **Temperature**, its own item under Models: the global value every model runs
  at unless it has its own on the [models](models.md) page or the agent sets
  one (`LLM_TEMPERATURE`, 0 to 2, applied at once). Machine-wide, so the
  Settings tab of a workspace does not show it.
- **Custom backends**: any OpenAI-compatible endpoint.
- **Local models**: Ollama and LM Studio, which need a running local server
  rather than a key; the hub only calls them at their base URL.
- **Agent execution**: the execution mode (in-process or Docker), the
  capability guard's mode (block, warn, off; `CAPABILITY_GUARD`, read live)
  and whether a per-agent exemption requires a container
  (`CAPABILITY_OVERRIDE_REQUIRES_CONTAINER`), see
  [tools-and-capabilities](tools-and-capabilities.md).
- **Web access**: the `fetch_url` limits and the global domain policy,
  written to `.env` and read live
  ([tools-and-capabilities](tools-and-capabilities.md), "Web access").
- Environment variables, per workspace.

Anything set here is global. A workspace's own Settings tab overrides the
parts that make sense per workspace ([workspaces](workspaces.md), "The
Settings tab").

Connectors are not here. Jira and GitLab live on the Connectors page
([connectors](connectors.md)), because a connector is something you attach
rather than a credential you set.

## After saving a first key

When a saved key is the first one for its provider, Settings reports the model
it switched on: its id, its price per 1M tokens and a link to the
[models](models.md#a-first-key-switches-on-a-model) page, where the choice is
changed. Model selection itself never lives in Settings. The response of the
save (`PUT /api/settings`, or the workspace settings save) carries the same
facts as `default_models`.

## Per-workspace overrides

A workspace can override the model default, the execution mode (in-process or
Docker) and environment variables. Anything not overridden falls through to the
global setting.

## Palette

Every color in the app comes from `src/theme.css`, generated by
`scripts/gen-theme.mjs`. A workspace can repaint it without touching that file:
in the workspace's Palette tab, "Default palette", set 2 to 4 base colors (a
brand color, a neutral tint, a success accent and a danger accent, the last
three optional) and everything else (11 shades per color, panels, borders,
text) is computed from them with a fixed lightness curve in OKLCH, so contrast
holds in both light and dark mode (`src/lib/palette.js`). Four presets ship
(Navy, the default; Forest; Slate; Sunset), plus Custom for anything else, and
Reset removes the override. The choice is stored at `settings.palette` next to
the workspace's other overrides. Resolution order in the browser: the current
workspace's default, then the built-in palette. It is decided once, in
`src/components/theme.js`, and re-applied whenever the theme or the palette
changes.

Before saving, the editor checks the picked brand color's contrast against
white at both readings (as text, as a button fill) and warns under WCAG AA's
4.5:1; it does not block saving, since the ramp's own construction already
keeps every *computed* shade safe regardless of what warns.

Canvas-style renderers (the flow editor, the reactflow and three.js views, the
process and math views, chart configs) read colors through
`src/lib/themeColors.js`'s `useThemeColors`/`cssVar` instead of holding hex
constants, so a custom palette reaches them too, live, without a rebuild.

## Reading the health of this

The health snapshot reports which keys are set (as booleans, never values),
and which provider is default. That is the quickest way
to check a configuration problem without opening the page. See
[service-health](service-health.md).
