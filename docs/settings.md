# Settings

Credentials and connection details. What models are offered and which is default
lives on the [models](models.md) page, not here.

## What is here

The page has a menu with three groups.

**Models**

- **Cloud providers**: the API key for OpenAI, Anthropic and Google, and a
  base URL where one applies. A key can be tested with the Test button.
- **Local models**: the base URL of Ollama and of LM Studio. They need a
  running local server rather than a key; the hub only calls them at their
  base URL.
- **Custom backends**: any OpenAI-compatible endpoint, with its own base URL,
  key, default model and extra headers.
- **Temperature**: the global value every model runs at unless it has its own
  on the [models](models.md) page or the agent sets one (`LLM_TEMPERATURE`, 0
  to 2, applied at once). Machine-wide, so the Settings tab of a workspace does
  not show it.

**System**

- **Agent execution**: live token streaming, the execution mode (in-process
  or Docker, with the image and network for Docker runs), the capability
  guard's mode (block, warn, off; `CAPABILITY_GUARD`, read live) and whether a
  per-agent exemption requires a container
  (`CAPABILITY_OVERRIDE_REQUIRES_CONTAINER`), the code runner (`run_code`
  provider, images and limits, see
  [tools-and-capabilities](tools-and-capabilities.md)), the [tool
  policy](tool-policy.md) and the task assignment mode.
- **Web access**: the search provider behind `web_search`, the `fetch_url`
  limits and the global domain policy,
  written to `.env` and read live
  ([tools-and-capabilities](tools-and-capabilities.md), "Web access").
- **RAG & vectors**: the vector database and the embedding model.
- **Logging**: the log level.
- **Demo workspace**: adds or removes the `demo` workspace ([demo](demo.md)).
- **First setup**: runs the first-run screen again.

Anything set here is global. A workspace's own Settings tab overrides the
parts that make sense per workspace ([workspaces](workspaces.md), "The
Settings tab").

Connectors are not here. Jira and GitLab live on the Connectors page
([connectors](connectors.md)), because a connector is something you attach
rather than a credential you set.

## After saving a first key

When a saved key is the first one for its provider, Settings reports the model
it switched on: its id, its price per 1M tokens and a link to the
[models](models.md#a-first-key-switches-on-a-model) page, where the choice is
changed. Model selection itself never lives in Settings. The response of the
save (`PUT /api/settings`, or the workspace settings save) carries the same
facts as `default_models`.

## Per-workspace overrides

A workspace can override provider keys and base URLs, the RAG settings, the
log level, the execution mode (in-process or Docker, with its image and
network) and the task assignment mode. Anything not overridden falls through
to the global setting. The model default is not among them: it is chosen on
the [models](models.md) page.

## Palette

Every color in the app comes from `src/theme.css`, generated by
`scripts/gen-theme.mjs`. A workspace can repaint it without touching that file:
in the workspace's Settings tab, Palette section ("Default palette"), set 2 to 4 base colors (a
brand color, a neutral tint, a success accent and a danger accent, the last
three optional) and everything else (11 shades per color, panels, borders,
text) is computed from them with a fixed lightness curve in OKLCH, so contrast
holds in both light and dark mode (`src/lib/palette.js`). Five presets ship
(Magenta, the default; Neutral; Forest; Slate; Sunset), plus Custom for
anything else, and "Clear default" removes the override. Magenta and Neutral
are styles: a white page with magenta buttons (dark page in the dark theme),
or graphite with no brand color. The choice is stored at `settings.palette` next to
the workspace's other overrides. Resolution order in the browser: the current
workspace's default, then the built-in palette (Magenta). It is decided once, in
`src/components/theme.js`, and re-applied whenever the theme or the palette
changes.

Before saving, the editor checks the picked brand color's contrast against
white at both readings (as text, as a button fill) and warns under WCAG AA's
4.5:1; it does not block saving, since the ramp's own construction already
keeps every *computed* shade safe regardless of what warns.

Canvas-style renderers (the flow editor, the reactflow and three.js views, the
process and math views, chart configs) read colors through
`src/lib/themeColors.js`'s `useThemeColors`/`cssVar` instead of holding hex
constants, so a custom palette reaches them too, live, without a rebuild.

## Reading the health of this

The health snapshot reports which keys are set (as booleans, never values),
and which provider is default. That is the quickest way
to check a configuration problem without opening the page. See
[service-health](service-health.md).
